The ingest service ([`apps/ingest/src/app.ts`](https://github.com/eviatarmor/Readmeter/blob/main/apps/ingest/src/app.ts)) listens on port 8090 by default. The SDK calls it for you; this page is for people writing an SDK, a proxy, or a monitor.

| Method | Path | Auth | Purpose |
|---|---|---|---|
| `GET` | `/healthz` | none | Liveness |
| `OPTIONS` | `/v1/*` | none | CORS preflight |
| `POST` | `/v1/batches` | API key | Store one SDK batch |
| `GET` | `/v1/bundle` | API key | Download the project's rule bundle |
| `GET` | `/v1/config` | API key | Read the project id and hash key |

## Authentication

Routes under `/v1` except preflight take a project API key as a bearer token:

```http
Authorization: Bearer rm_live_...
```

The key is looked up by its SHA-256 among keys that are not revoked. A missing header, a header that does not start with `Bearer `, or an unknown or revoked key returns:

```http
HTTP/1.1 401 Unauthorized
Content-Type: application/json

{ "error": "unauthorized", "detail": "missing or invalid API key" }
```

If the key has a non-empty origin allowlist and the request sends an `Origin` header that is not in the list, the route returns:

```http
HTTP/1.1 403 Forbidden
Content-Type: application/json

{ "error": "origin_not_allowed" }
```

Requests without an `Origin` header pass the origin check. See [Security](/docs/self-hosting/security#origin-allowlists).

## Errors

Error responses are JSON with an `error` code and, for most codes, a `detail` string:

```json
{ "error": "rate_limited", "detail": "too many batches" }
```

| Status | `error` | When |
|---|---|---|
| 400 | `bad_batch` | The core could not decode the body |
| 401 | `unauthorized` | Missing or invalid API key |
| 403 | `origin_not_allowed` | `Origin` not in the key's allowlist |
| 413 | `batch_too_large` | Body over 1 MiB, or more than 10,000 events or 1,000 findings in the batch |
| 429 | `rate_limited` | The client IP's (browser requests) or the project's rate limit bucket is empty. Has `Retry-After` |
| 500 | `internal` | The core failed, the store write failed, or the SDK bundle is not configured |
| 503 | `busy` | 64 store writes already in flight. Has `Retry-After: 5` |

## `GET /healthz`

No authentication. Returns `200` with the plain text body `ok`. It does not check the database.

## CORS

All `/v1/*` routes use the same CORS settings:

- `Access-Control-Allow-Origin` reflects the request's `Origin`, for any origin. Preflight carries no key, so the allowlist cannot be checked there; it is checked on the real request.
- Allowed methods: `POST`, `GET`, `OPTIONS`.
- Allowed request headers: `authorization`, `content-type`.
- `Access-Control-Max-Age: 600`.

## `POST /v1/batches`

Stores one batch produced by the SDK core's `flush()`.

### Request

- Header `Authorization: Bearer <api key>`.
- Body: the raw bytes returned by `flush()`, at most 1,048,576 bytes. The `Content-Type` header is not checked. The JS SDK sends `application/octet-stream` with `fetch`, and sets `keepalive` for the flush on `pagehide` and on process exit; a `sendBeacon` caller that omits the content type is accepted too.

### Processing

The checks run in this order, and the first failure answers:

1. Body size (`413`).
2. Per-IP rate limit, only for requests with an `Origin` header (`429`, detail `too many batches from this address`).
3. API key (`401`) and origin (`403`).
4. Rate limit for the project, shared by all its keys (`429`, detail `too many batches`).
5. Writes in flight (`503` with `Retry-After: 5`).
6. The Rust core decodes the batch (`400 bad_batch`), checks the event and finding counts (`413 batch_too_large`), and runs `window` and `aggregate` rules for the project.
7. One Postgres transaction inserts the batch row, the events in chunks of 1,000, and upserts the findings (`500 internal` if it fails).

Both `429` answers carry `Retry-After` in whole seconds, at least 1. The project limit is the project's own `ratePerMin` (console project settings) or `READMETER_RATE_PER_MIN` (default 600 per minute, burst 100); the per-IP limit is `READMETER_RATE_PER_IP_PER_MIN` (default 120, burst 20). Burst is `max(1, ceil(rate / 6))`. The limits are held in each ingest process, not in Postgres, so several ingest instances each apply them separately. See [Security](/docs/self-hosting/security#rate-limits-and-backpressure).

Findings that share project, rule, session, callsite and template are merged: `occurrences` is summed, `first_seen` and `last_seen` are widened, and severity, message, evidence, wasted units and the callsite label take the latest values. Window and aggregate rules run with the project's rule overrides. Ingest loads those overrides on each batch and rebuilds that project's rule state when they change.

### Response

`202 Accepted` only after the transaction has committed:

```json
{
  "events": 42,
  "findings": 1,
  "evaluator_findings": 2,
  "dropped_events": 0
}
```

<TypeTable
  type={{
    events: { type: "number", description: "Events in the batch that were stored." },
    findings: { type: "number", description: "Findings the SDK produced from local rules (source sdk)." },
    evaluator_findings: { type: "number", description: "Findings the server evaluator added from window and aggregate rules." },
    dropped_events: { type: "number", description: "Events the SDK dropped from its buffer before this batch, as reported in the batch." },
  }}
/>

A client should keep the batch and retry after `Retry-After` on `429` and `503`. A `400` or `413` batch will not succeed on retry.

## `GET /v1/bundle`

Returns the SDK rule bundle (`bundle.bin`, built by `readmeter-rulec`) for the key's project.

### Request

- Header `Authorization: Bearer <api key>`.
- Optional `If-None-Match` with an ETag from an earlier response. A list of ETags, weak ETags (`W/"..."`) and `*` are accepted.

### Response

- `200` with `Content-Type: application/octet-stream`, the bundle bytes, and an `ETag` header.
- `304` with the `ETag` header and no body, when `If-None-Match` matches.
- `500 internal` when ingest was started without an SDK bundle.

The ETag is the first 16 hex characters of the SHA-256 of the bytes served. When the project has rule overrides (set on the console's Rules page), ingest merges them into the bundle before serving it, so the bytes and the ETag differ from the base bundle. A project with no overrides gets the file from `READMETER_SDK_BUNDLE` unchanged.

## `GET /v1/config`

Returns the key's project and its hash key.

### Request

- Header `Authorization: Bearer <api key>`.

### Response

```json
{ "project": "proj_abc123", "hash_key": "000102030405060708090a0b0c0d0e0f" }
```

<TypeTable
  type={{
    project: { type: "string", description: "Project id the key belongs to." },
    hash_key: { type: "string", description: "32 lowercase hex characters. The SDK uses it as the key for keyed hashes." },
  }}
/>

## Example

```sh
curl -i http://127.0.0.1:8090/v1/config \
  -H "Authorization: Bearer rm_dev_key"
```

With the local seed data this returns project `proj_demo` and hash key `000102030405060708090a0b0c0d0e0f`.
